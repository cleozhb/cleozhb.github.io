code agent 系统设计

Created2026-06-21|Updated2026-07-06
|Post Views:

Code Agent作为唯一真正大规模落地的工业级应用背后到底做了啥？Claude code 这样的code Agent是怎么运行的？前段时间自己也开发了一个简易版本的code Agent runtime，目前还是本地CLI版本。经过调研发现事情没有这么简单。Claude 桌面 APP里面的Claude code 是支持在本地运行同时也支持云端沙箱运行的，而且Claude这样的应用肯定同时有百万用户发请求，这时候的系统架构又是怎么样的演进？接下来分4个部分来介绍这些设计：

  1. 需求分析
  2. 本地机器环境执行架构
  3. 云端沙箱环境执行架构
  4. 云端沙箱同时支持百万并发请求的架构

需求分析

先来看看一个单机版的 code Agent 需要实现什么功能：

功能性需求 Functional Requirement

  1. 输入任务：CLI或用户页面中接收用户输入自然语言
  2. 代码库理解能力：读文件，搜索代码，构建上下文
  3. 代码生成&编辑：Agent能够编辑现存的文件也可以写新文件
  4. 执行命令：执行命令，生成输出
  5. 迭代循环：测试失败时Agent能读到错误并修正
  6. 检查点checkpoint：用户能够回滚到这个session之前的任意版本
  7. 权限控制：敏感操作需要用户确认(原则：无修改、可回滚的操作auto模式；不可逆的操作人工审批，删除文件，运行shell命令)

非功能性需求 nonfunctional requirement

  1. 安全性，Agent 决不能自己执行不可逆的操作
  2. 延迟：首token延迟不超过2秒，用户需要能实时知道Agent现在在干啥
  3. 可靠性：如果在执行任务过程中崩溃了，不能有只编辑了一半的文件，Agent所做的操作必须是原子的，可恢复的。而且需要能从指定的地方恢复。
  4. 成本优化：token使用效率必须是一个设计约束
  5. 上下文限制：Agent必须给模型展示正确的代码片段
  6. 多模型支持，不能依赖单一模型供应商

本地机器环境执行架构

一、 核心中枢：服务端执行环境

云端大脑+本地执行。服务端的职责是思考、规划、记忆和调用大模型。它由以下几个核心组件构成：

1. Orchestrator Agent (主Agent)

这是整个系统的大脑中枢。它的主要职责不是亲自写每一行代码，而是做项目管理：

  • 规划与委派 (Plan/Delegate)： 接收到用户的任务后，将其拆解成一个个子步骤，并委派给 Sub Agent 去做。
  • 循环迭代 (Iterate)： 根据本地执行返回的结果（成功或报错），决定下一步做什么，直到任务彻底完成。
  • 上下文管理 (Context Management)： 大模型的上下文窗口是有限的。主Agent会在对话太长时将其压缩为Summary，决定什么时候停止，始终掌控全局。

2. Sub Agent

  • 上下文隔离。如果主Agent把所有的代码细节都塞进脑子里，它很快就会“死机”或产生幻觉。子Agent专门负责解决单一的、具体的子任务（比如专门负责写一个特定函数的测试用例）。处理完后，只把“结果”汇报给主Agent，保证了主Agent的上下文始终干净清爽。

3. 支撑系统（记忆&上下文）

  • Context Engine (上下文管理 / 代码库)： 负责理解你的整个项目代码库。它能生成代码地图（repo map），提取函数签名。这意味着Agent不需要把几万行代码全读一遍，而是像查字典一样，按需读取所需文件，极大地节省了Token和时间。
  • Session Store (会话管理 / 短期记忆)： 保存历史记录和Checkpoint（检查点）。这是工程化非常重要的一环。如果Agent改错了代码导致崩溃，系统可以通过Checkpoint进行回滚（Rollback）和崩溃恢复，保证了系统的鲁棒性（稳定性）。

4. Model Gateway (模型路由)

  • 通过引入网关层，可以灵活地将请求路由给 OpenAI、Anthropic 或其他本地开源模型。这样做既能防止供应商锁定和限流，又能根据任务复杂度动态选择最划算的模型。

二、 执行终端：本地机器环境

本地环境的职责是接收指令、安全检查并执行物理操作。

1. Agent 用户界面 CLI

这是用户与系统交互的入口。通常是一个命令行工具（CLI），你在这里输入任务，例如：“帮我找一下登录接口的bug并修复”。

2. Permission Scope Layer (权限策略层 ) —— 极其关键

  • 安全兜底。 大模型是不可控的，有时可能会生成极具破坏性的指令（比如 rm -rf / 删除所有文件）。这个权限层卡在云端指令和本地工具之间，负责拦截高危操作，或者在执行敏感操作（如覆盖重要文件、执行Bash命令）前弹窗询问用户是否允许，确保你的本地机器绝对安全。

3. 工具系统 (Tool System)

  • 文件操作： 读文件、写/编辑文件。
  • 代码检索： grep（全局搜索）、list（列出目录）。
  • 环境交互： 执行bash命令（比如运行 npm run test 或 python main.py）、操作Git（提交代码）。
  • 外部信息： web search（当遇到没见过的新库时，Agent可以自己去搜文档）。

4. 底层基座

所有工具最终都作用于你本地的 文件系统 (File System) 和 终端 (Terminal)。

三、 跑通一个业务闭环（数据流转）

以输入“帮我写一个按时间排序的函数”为例，系统的运转流程如下：

  1. 用户输入：你在本地CLI输入需求。
  2. 大脑思考：主 Agent (Orchestrator) 收到需求，结合 Context Engine 知道该把代码写在哪个文件里。
  3. 下发指令：主 Agent 生成了一个“写文件”的工具调用指令（Tool Call）。
  4. 安全审查：指令到达本地，Permission Layer 检查发现只是普通的写文件，放行。
  5. 本地执行：本地“写文件”工具在你的文件系统里修改了代码。
  6. 反馈结果：工具将“写入成功”或“语法错误（Error）”反馈给云端（Output/Error 链路）。
  7. 循环校验：主 Agent 收到反馈，可能还会调用 bash 工具跑一下单元测试。如果报错了，就再循环一次，直到测试通过。

这个设计解决了当前 LLM（大语言模型）辅助编程的几个痛点：

  1. 上下文不够用 -> 用 Context Engine 按需读取 + Sub Agent 隔离解决。
  2. 大模型容易乱改代码 -> 用 Session Store 检查点回滚解决。
  3. 云端执行不安全/不方便调试 -> 用 本地执行 + 权限管控层 解决。
  4. 大模型API贵或不稳定 -> 用 Model Gateway 路由解决。

整体实现需要重点投入 “Context Engine 的精准度” 和 “Permission Layer 的边界设计” 上，这两个是决定该产品用户体验好坏的核心。

云端沙箱环境执行架构

云端大脑+云端执行。所有的思考、存储、甚至代码的实际修改和执行，都在服务器上完成。

一、 接入与安全网关层 (Gatekeeper)

因为环境从“用户私有本地”变成了“公共云端”，所以多租户管理和防滥用成了第一道门槛。

  • API Gateway (API 网关)： 网关负责统一接收请求、路由分发、防止恶意攻击。
  • Auth Service (身份验证 & 套餐限流)：
    • 身份验证：确认“你是谁”（比如通过 Token 或 API Key）。
    • 套餐限流 (Rate Limiting)：云端执行和调用大模型都是要烧钱的。

二、 核心中枢与状态持久化层 (Brain & Memory)

核心变成了 Orchestrator Service（编排服务），强调了它的服务端属性，并且它增加了外部存储依赖。

  • Orchestrator Service (主服务)： 依然负责 Plan -> Delegate -> Iterate 的核心业务循环。
  • 存储层 (Storage Layer)：状态管理的根本转变
    • 在上一版本地架构中，状态可以存在用户本地硬盘。而在云端，服务是无状态的（Stateless），随时可能重启或扩缩容，所以必须依赖外部数据库。
    • Redis：作为高速缓存。保存“正在处理的会话上下文”、“当前执行到哪一步了”。因为读写极快，能支撑高频的循环调度。
    • MySQL：作为持久化数据库。保存“用户的历史对话记录”、“账单信息”、“长期的代码修改记录（审计日志）”。

三、 核心焦点：沙箱执行环境 (Sandbox) —— 云端隔离沙箱

这是整个架构区别于前者的最大核心，也是技术难度最高的地方。

因为在云端执行大模型生成的代码（尤其是 Bash 命令）是极其危险的。如果不加隔离，大模型可能生成一句 rm -rf /，就把你的整个服务器删库跑路了；或者生成一段恶意代码去偷看其他用户的项目。

  • 沙箱机制 (Sandbox Isolation)：
    • 为每一个用户的每一次任务，动态创建一个完全隔离的、用完即毁的微型虚拟机或容器（通常使用 Docker、Kubernetes，或者更底层的 Firecracker 等技术）。
    • 安全保障：在这个沙箱里，Agent 可以随意调用读写文件、grep、git、执行 bash 等工具。即使代码有毒（比如死循环、内存溢出），也只会搞死这一个沙箱，绝对不会影响宿主机和其他用户的环境。
  • 工具系统：图中的“读文件、执行bash”等操作，全部都是作用于这个云端沙箱里的临时文件系统中。

四、Pros and cons

优势

  1. 用户体验“极轻”：用户完全不需要在本地配置复杂的环境（不用装 Python、Node.js、各种依赖库）
  2. 环境统一：彻底消灭了“在我的电脑上能跑，在你那里报错”的问题。因为运行环境是云端统一提供的标准沙箱。
  3. 安全性：无论 AI 写出什么毁灭性的代码，用户的本地电脑绝对安全。

劣势

  1. 云端成本极其高昂：需要为成千上万的用户准备计算资源。启动沙箱、分配内存、跑代码，这都是服务器成本。
  2. 私有化问题：用户的代码本来在自己本地硬盘里。如果要在云端跑 Agent，用户必须先把自己的整个代码库上传到云端的沙箱里。改完之后，还要再同步回本地。对于企业级的大型机密项目，往往不能接受将代码传到外部云端。
  3. 网络延迟：每一次输入、每一个反馈都要经过网络，实时体验不如本地执行流畅。

总结

  • 本地执行：更适合作为开发者的高级辅助工具（类似于本地IDE插件），处理本地既有项目，保护隐私，无服务器执行成本。
  • 云端沙箱：更适合作为在线编程平台、云端 Agent 原生应用，主打开箱即用。

百万并发请求的云端架构

一、 流量洪峰缓冲层：异步解耦

引入 消息队列 MQ 和 配套的消费消息服务 **Session Worker，**将接收用户请求和处理解耦。

  • 削峰填谷。用户的请求（API Gateway）不再直接打给处理中枢，而是全部扔进 MQ（比如 Kafka/RabbitMQ）里排队。
  • Session Worker 根据当前系统的空闲算力，平滑地从 MQ 里拉取任务，然后启动/唤醒一个 Orchestrator 来处理。
  • 结果：无论流量涌来多猛，系统都不会挂，最多只是用户排队等候的时间稍微变长一点。

二、 核心中枢进化：无状态与水平扩容 (Stateless & Horizontal Scaling)

需要无限扩展，且绝不能因为某台服务器宕机而导致用户任务丢失。办法就是将Orchestrator（主Agent）改造为无状态服务（Stateless）。

  • Orchestrator 无状态服务。服务器的内存里不保存任何会话记忆。
  • 状态外置：所有的 AgentLoop（LLM调用、工具调用、执行结果），每走一步，都会立刻保存到 Redis（实时缓存） 和 MySQL（持久化） 中。
  • 任意接管。哪怕正在循环的 Orchestrator 实例突然挂了，可以瞬间启动一个新的实例，新实例从 Redis 读取上一步的状态，无缝继续执行，用户完全无感知。这使得系统可以随时扩容到上万个节点。

三、 成本与性能优化层：Prompt Cache (大模型缓存)

百万并发意味着海量的 Token 消耗，直接调用 OpenAI/Anthropic 消耗巨大；且大模型响应慢，延迟高。解法是在 Model Gateway 中引入了 Prompt Cache。

  • 复用思考过程。Redis（精确匹配）+ 向量数据库（语义相似度匹配）。代码 Agent 在执行时，会有大量的重复上下文（比如项目的通用设定、常用的系统指令、重复的代码结构）。用户输入一段 Prompt，网关层会去数据库里找，看看以前有没有人问过一模一样（或语义极其相似）的问题。如果找到了，直接把上次存下来的答案返回给用户，不调用大模型。

四、 核心安全防线：Guardrails (安全护栏)

所有生成的 Tool call，在下发给执行端之前，必须经过这道护栏。

  • 三重机制：
    • Auto Confirm (自动放行)：读文件等安全操作。
    • Deny (直接拒绝)：例如 rm -rf 等黑名单高危指令。
    • 人类审批：对于敏感操作（如覆盖核心代码），暂停执行，要求用户在界面上确认。

五、 执行与回滚层：混合架构与 Shadow Git (影子版本库)

  • 本地沙箱隔离：即使在本地执行，也放在了隔离环境中，保证本地系统安全。
  • 终极杀手锏：Checkpoint Layer (Shadow Git)。
    • 在大模型修改你本地的几十个文件之前，系统会在底层自动建一个隐形的 Git 节点（Shadow git snapshot）。
    • 如果 Agent 陷入死循环、或者把代码改乱了、编译不通过，系统可以瞬间触发回滚（Rollback）。

总结

  1. 高并发可用：用 MQ 解耦，用 Redis/MySQL 抽离状态，让核心算力可以无限水平扩展。
  2. 成本控制到极致：用 Prompt Cache 省大模型的钱；
  3. 安全：加上了 Guardrails 护栏和 Shadow Git 回滚，即使 AI 不稳定，也有人类审批和回滚机制兜底。
