背景

Claude code横空出世也有一段时间了，对AI Agent的好奇心也达到了前所未有的高度。想要体验AI Agent已经很久了，各种框架也听得眼花缭乱 Langchain, crewAI, n8n, AutoGPT, Dify等等。看了很多博客，发现最终还是要回归到自定义构建块构建人工智能应用。因为实际上有用的大多数还是传统软件工程能控制的确定性软件，LLM只是恰好加了进去发挥作用了而已。但是大多数框架都推行：让LLM理解一切。实际上我们并不想让LLM决定一切，只需要LLM完成它擅长的根据上下文推理，而其他的具体操作由程序员确定性的代码完成。

解决方案比大多数的框架要简单，通常分为下面的步骤：

  • 拆分任务为基础组件
  • 用传统的软件工程解决每个问题
  • 当无法用确定性代码解决问题时用LLM解决

LLM是整个架构中最昂贵的部分，虽然非常强大，但是在必要的时候使用就可以了。有人工干预和全自动系统之间存在巨大差异，大多数情况下我们并不是要构建一个像ChatGPT、Cursor这样的用户处于循环中的工作流，我们要构建的是一个后台自动化以提高工作效率的工作流。

当进行LLM调用时，一切都与上下文工程有关。为了得到一个好的答案，需要在正确的时间将正确的上下文发送到正确的模型。需要预处理所有可用的信息、提示和用户输入，历史记录，以便LLM能够轻松可靠地解决问题。这是与LLM合作的最基本技能。

7个积木

工作流准确点说就是DAG(directed acyclic graphs)有向无环图，工作流中的大多数步骤应该是常规代码而不是LLM调用。只需要七个核心构建块来解决几乎所有的业务问题。把你的大问题分解成更小的问题，然后使用这些链接在一起的构建块来解决每个问题。

Brain

向LLM发送请求，LLM会对此进行思考，然后发送回文本。就是这样。没有这个就是常规软件。棘手的部分不是LLM本身，而是你需要围绕它构建的所有其他东西。

Memory

Context persistence across interactions 跨交互的上下文持久性

LLM是无状态的。因此，每次都需要手动传入对话历史记录。这只是存储和传递对话状态，这是我们在web应用程序中一直在做的事情。

Tools

外部系统集成能力 External system integration capability

大多数时候需要LLM来真正做事情，而不仅仅是聊天。纯文本生成作用有限，在实际生产环境我们需要调用API、更新数据库或读取文件。LLM说“我需要用这些参数调用这个函数”，你的Tool代码会处理实际的执行。这只是普通的API集成，LLM选择要调用的tool并提供json格式的输入参数。

Validation

您需要确保LLM返回与预期模式匹配的JSON。LLM是概率性的，可能会产生不一致的输出，可以根据预定义的结构验证JSON输出。如果验证失败，可以将其发送回LLM进行修复。这可以确保下游代码能够可靠地处理数据。使用Pydantic、Zod或数据类等工具进行重试逻辑的正常模式验证。

Control

你不希望LLM做出每一个决定，有些事情应该由常规代码处理。使用if/else语句、开关和路由逻辑来根据条件引导

Recovery

总会有些地方出错，API会调不通，LLM会返回废话，可能会被限频，需要try catch模块来处理一些异常

Feedback

有时需要一个人在LLM上线之前检查它的工作。有些决策对于完全自动化来说太重要或太复杂了，比如向客户发送电子邮件或进行购买。添加批准步骤，在执行之前，人类可以在其中进行审查和批准。

先说明一下Claude生态下自定义工具如何用

工具定义时，需要提供极其详细的描述。包括：

  • 该工具的功能是什么
  • 何时应该使用（何时不应该使用）
  • 每个参数的含义及其对工具行为的影响
  • 任何重要的警告或限制，例如如果工具名称不清楚，工具不会返回哪些信息。你能给Claude提供的关于你的工具的背景越多，它就越能决定何时以及如何使用它们。每个工具描述至少3-4句话，如果工具复杂，则更多
