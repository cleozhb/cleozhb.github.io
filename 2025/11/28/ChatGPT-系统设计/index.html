ChatGPT 系统设计

Created2025-11-28|Updated2026-07-06
|Post Views:

ChatGPT作为OpenAI的super App，服务是怎么搭建起来的？调研后画个图来记录一下。

如何构建一个类似ChatGPT的大语言模型系统，周活用户达到 10亿，每天发送超过25亿条消息

功能性需求：

  • 返回AI生成的内容回答问题 Accepts user input like prompts or queries & return AI-generated response
  • 流式输出 Support streaming token by token (like typing effect)
  • 多模型支持 Support multiple models
  • 支持用户上传自定义文档 Support custom documents and updated data(RAG)
  • 用户隐私保护

非功能性需求:

  • 多轮对话 自动获取上下文 Context preservation 使用聊天记录作为上下文
  • 低延迟 Low Latency: < 1 second 这是一个预测模型，不可能达到 ms级别的延迟，至少可以尝试1s
  • 优化成本 Cost Efficient 模型很大，且部署在多个服务器上，如何降低成本？如果有一些通用的查询，如何针对这些查询进行优化？
  • 提高响应吞吐量 Throughput at scale 如何获得良好的吞吐规模？如何批处理多个查询？
  • 限流 Rate Limiting - Quota of queries 不同套餐有不同的token限制

过一遍整个流程骨架，先不看限流、安全等问题，不是不重要，只是非核心功能。

编排类服务器query server

首先我们需要一个编排类服务器query server ，用来和用户建立长连接，因为大模型现在的transformer架构是自回归的，所以不能像传统http协议那样等到一个回包一起返回给用户，那样太慢了，因此需要长连接，用到SSE（Server-Sent Events）这样流式传输协议。

SSE的技术特点：

  1. 单向通信： 只能是 服务器 -> 客户端 发送数据。客户端建立连接后，只能被动接收。
  2. 基于 HTTP： 它没有发明新协议，就是在普通的 HTTP 协议上做文章。服务器只需在响应头里加一句 Content-Type: text/event-stream，浏览器就知道：“哦，这不是一个普通的网页，这是一个数据流，我要一直等着接收。”
  3. 文本格式： 传输的数据只能是文本（UTF-8 编码）。
  4. 自带重连： 浏览器原生支持，如果连接断开了，浏览器会自动尝试重新连接。

embedding服务

用户请求到达query server之后，需要进行embedding转化为LLM能理解的高维向量。

推理服务

重中之重推理服务。这里面涉及到很多技术要点，就按照我的理解先写。先说几个必须理解的概念：

  1. 模型分片：现在模型都很大，一张GPU卡肯定不够，所以要进行分片。
  2. KV cache：用来避免重复计算历史 Token 的注意力机制（核心技术 PagedAttention），KV cache的大小不容小觑，非常占GPU显存，这也是为什么模型的上下文不会很大的重要原因，主流模型的上下文长度在200K，最多1M。
  • 在流水线并行中shard 1 只有第 1-10 层的参数，所以 shard1 的GPU显存里只存第 1-10 层的 KV Cache
  • 注意力机制（Attention Heads）是被切分的。假设模型有 32 个头（Heads），两张卡做 TP，那么 GPU 1 只计算和存储头 1-16 的 KV Cache，GPU 2 只存储头 17-32 的 KV Cache。

  1. MOE：混合专家模型，就是说模型那么大那么多参数，并不是激活全部的，而是激活部分参数，并保证回答的鲁棒性。dense模型会激活所有的参数，经过所有的分片。MOE模型路由模型和模型的其他参数一起训练，在推理时决定要激活哪些参数，在哪些分片上进行计算，通常是从 N 个专家中选出 Top-2。

  2. 投机解码：先将用户query发送给较小的模型，获得一些4,5个左右推测性的答案，也作为上下文的一部分提供给LLM选择，LLM最终决定是否采纳还是重新生成

推理过程

查询到达，就会进入分片的第一层，一直传递下去，直到最终输出 第一个token。因为大模型是一个自回归 Auto regressive 模型，所以这个过程会循环直到输出 EOS(end of sequence)或达到 max token limit。

  1. 调度与批处理（Continuous Batching）：上游会维护一个调度队列攒一批请求，一起发给GPU进行推理提高吞吐。
  2. Prefill（预填充阶段）：计算用户的 Prompt，生成第一批 KV Cache，并吐出第一个 Token。这个阶段计算密集
  3. Decode（解码阶段）：开始逐字生成。网络中无数个 Token 在 TP 和 PP 组成的 GPU 矩阵中穿梭

每次前向传播生成一个 Token，更新一次 KV Cache，直至生成结束符号（EOS）

  1. 显存回收：请求结束，PagedAttention 释放该请求占用的 KV Cache 物理块，留给下一个请求使用

分片方法

分片方法：（通常是 TP + PP 的组合。比如一台机器 8 张卡做 TP，然后多台机器之间做 PP，组合成一个完整的模型推理实例）

  1. 流水线并行（Pipeline Parallelism, PP）按层切分

  2. 把模型的几十上百层（Layers）像流水线一样切断。例如一个 80 层的模型，GPU 1 负责第 1-10 层，GPU 2 负责第 11-20 层…

  3. 数据像接力棒一样穿过不同的 GPU，节点间的通信量相对较小，直到最后一张 GPU 吐出结果

  4. 张量并行（Tensor Parallelism, TP）按矩阵切分

  5. 在模型的同一层内部进行切分。Transformer 中的矩阵乘法非常大

  6. TP 会把一个大矩阵切成几块，请求的数据被复制到参与 TP 的所有 GPU 上

  7. 每张 GPU 并行计算自己负责的那部分矩阵，然后通过通信将结果合并，再进入下一层

  8. 需要极高的通信带宽，通常只能在同一台物理服务器内（通过 NVLink 连接的 8 张 GPU）使用

  9. 专家并行（Expert Parallelism, EP）：针对 MoE 模型

  10. 对于 deepseek 这种混合专家模型（MoE），不同 GPU 上存放不同的“专家网络”。

Prefill & Decode

每个 Transformer 架构的大型语言模型的推理请求都会经历两个阶段：prefill 阶段和decode 阶段。prefill 阶段会对输入的 prompts 进行处理，而decode 阶段则主要是利用自回归的方式来生成 tokens。一个请求仅需要经历 1 次prefill 阶段，但却需要经历多次decode 阶段，每生成 1 个 token 就需要 1 次decode 阶段，这一特性也将显著影响到大语言模型的整体推理效率。

Transformer 架构的推理从 prefill 阶段 开始，在该阶段中，模型会并行处理给定 batch size 下的所有的输入 tokens。此时，Transformer 解码器的输入是一个形状为 的张量 ，其中表示批处理中所包含的请求个数， 表示每个请求的 prompt 长度，也就是给定查询中输入 tokens 的数量， 是模型的（嵌入向量）维度（例如，对于 GPT-3 模型来说， 的值为 12288）。

上下文 & 多轮对话

这个部分可以做出很多花样，最简单的就是维护一个message 列表，然后滑动窗口提取历史记录，传给LLM。这么做的缺点是重要信息遗漏，暴力截断。已经有一些常用的优化方法，但是也各有各的缺点：

优化方法一：早期历史摘要 + 最近窗口。这种方法的主要问题是：

  1. 摘要会丢细节，大模型生成的摘要可能会错。
  2. 何时触发？估算 token 超过阈值触发的话不看任务阶段，可能刚完成一堆探索、还没干活时就压缩，把待用的线索总结掉。也可能某个长工具输出把 token 顶高，导致无关历史被压缩。
  3. 最近窗口如何取舍？如果一次任务中 agent 跑了很多 tool call，这些都算在同一轮附近；如果用户连续发很多短消息，真正重要的前文可能很快被挤进摘要区。
  4. 一旦早期消息被摘要替换，原始 tool result / assistant reasoning /用户原话在当前 conversation 里就没了。除非另有 trace 或 checkpoint，否则模型没法“展开摘要看原文”。
  5. 压缩本身消耗 token 和钱。这部分成本不容小觑，在使用Claude code的时候就能感受到一次压缩会花很多钱。

优化方法二：用 RAG 检索相关历史再注入 context。这种方式最大的好处是能找回很早以前但仍然相关的信息。

缺点：

  1. 最大的问题是检索可能找错，相似不等于相关。召回和排序难调。
  2. 历史片段缺少完整因果链。
  3. 需要维护索引。每轮对话、工具结果、文件修改、测试结果都要切 chunk、打标签、embedding、存储、更新。代码量和系统复杂度会明显上升。
  4. 隐私和成本。如果用外部 embedding API，要考虑把对话和代码片段发出去的问题；如果本地 embedding，又要处理模型、速度、存储。

RAG

用户上传文档，进行chunking，embedding 存入向量数据库。在query server 构造上下文的时候根据用户query 的embedding结果召回相关性高的文档，注入上下文给模型做参考。这部分细节也很多，是现在企业内用大模型的重点技术。

安全

在用户输入输出进入模型的时候需要过滤用户隐私，检测合法合规敏感信息、有害信息
